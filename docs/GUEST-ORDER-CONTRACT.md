# Гостевая заявка — контракт 10А

## Дополнение 10Б — действует с 11 октября

Ниже сохранён исходный контракт формы 10А. Серверная реализация 10Б теперь существует, но включена только в явно изолированном локальном тесте; обычный сайт по-прежнему показывает «Проверить данные» и не принимает заявки. Текущие типы — `lib/order-contract.ts`, результат проверки — [STEP-10B-REVIEW.md](STEP-10B-REVIEW.md).

`POST /api/orders/session` с `{}` сначала устанавливает гостевую HttpOnly-сессию. `POST /api/orders` принимает `{order: GuestOrderRequest, expectedPrices: [{variantId, unitPriceKopecks}]}` с UUID в `Idempotency-Key`. Ожидаемая цена сравнивается с серверной, но не определяет сумму. Ключ попытки уникален глобально, повтор возвращает номер только своей сессии. В теле нет токена сессии.

Текущие ответы: успех `200 {ok:true, orderId}`, ошибки формы `400 validation`, запрет источника `403 validation`, отсутствующая сессия `401 session`, изменившиеся цена/количество `409 cart_changed` с полным `quote`, конфликт попытки `409 conflict`, лимит `429 rate_limited`, недоступность/неподтверждённое сохранение `503 unavailable/network`. Неизвестная цена/наличие возвращает `409 unavailable`. Все ответы `no-store`. До записи подтверждение успеха не выдаётся; сохранение заявки и задания Telegram атомарно. Отправка Telegram ещё не реализована.

Клиент хранит в sessionStorage лишь ключ и солёный хеш, повторяет неподтверждённый снимок и блокирует его изменение. Изменившийся состав требует отдельного согласия. После успеха вычитаются только отправленные количества. Поля контактов не сохраняются в браузере; после перезагрузки их нужно повторить точно. Живой СДЭК отложен, ПВЗ без серверного подтверждения не принимается; реальная 1С и production-хранилище остаются внешними зависимостями.

## Исторический контракт 10А

Рабочий checkout D:/grace. Исходное задание: `D:/Grace-Astra-Prompts/prompts/19-step-10a.md`, с [последними ответами владельца](STEP-10A-OWNER-DECISIONS.md). Это договорённость для реализации 10Б, а не работающий сервер приёма заказов. Доставка только по России; СДЭК в ПВЗ из списка или курьером, а также почта.

## Реализовано сейчас

`/bag` ведёт на `/checkout`. Форма без регистрации показывает точные варианты, количества, сумму товаров и отдельное пояснение «Стоимость доставки уточнит менеджер». Сумма считается в копейках; любая неизвестная цена делает весь итог неизвестным. Цена не заменяется нулём, доставка не включается в сумму.

`lib/guest-checkout.ts` определяет `CheckoutFields`, `GuestOrderRequest`, `GuestOrderResult`, проверку полей, подготовку данных и интерфейс отправки. `submitGuestOrder()` всегда возвращает `unavailable`: нет HTTP-запроса, записи заказа, отправки WhatsApp, очистки корзины или благодарности. В интерфейсе явно указан проверочный режим; кнопка называется «Проверить данные». Не использовать реальные контакты при проверке.

Форма хранит ввод только в React state. Ошибка и смена способа доставки не стирают введённые значения; в будущий запрос попадает только выбранный способ. Изменение города сбрасывает ранее выбранный ПВЗ, чтобы не отправить заказ в другой город. Перезагрузка/уход со страницы сбрасывают форму. Сохранение гостевого профиля и восстановление через проверенный телефон относятся к 11А–11В. Ни localStorage, ни URL, ни логи не получают контактные поля. СДЭК передаётся только населённый пункт для поиска, а не имя, телефон, комментарий или корзина.

## Данные запроса

Предлагаемый будущий `POST /api/orders`, JSON, `schemaVersion: 1`. Маршрут в 10А не создан.

| Поле | Правило |
|---|---|
| `customer.fullName` | Фамилия и имя, отчество при наличии; до 150 символов; Unicode-буквы, пробелы, дефисы и апострофы. Пробелы нормализуются. |
| `customer.phone` | Телефон с кодом страны, 8–15 цифр, нормализуется в `+…`. Российские 8/7 с 11 цифрами приводятся к +7. Это проверка формата, не владения номером. |
| `delivery.method` | Только `cdek` или `post`. Для СДЭК `mode` = `pickup` / `courier`. |
| `delivery.countryCode` | Только `RU`. |
| СДЭК ПВЗ: `pickupPoint` | Объект `{code, city, address, countryCode:'RU', cityCode, region?, workTime?}` из официального API. cityCode и region различают одноимённые населённые пункты. Ручная подмена ПВЗ не предусмотрена. Код до 50, город до 120, адрес до 250 символов. Живой список зависит от доступности API — см. CDEK-INTEGRATION.md. |
| Курьер/почта: `city` | Населённый пункт, 2–120 символов. |
| Курьер/почта: `region` | Область/край/республика, 2–120 символов. |
| Почта: `postcode` | Шесть цифр; формат для адреса в России. Это не проверка существования отделения. |
| Курьер/почта: `address` | Улица, дом и корпус, 4–250 символов. Курьеру почтовый индекс не требуется. |
| Курьер/почта: `apartment` | Квартира/офис, необязательно, до 30 символов. Пустое поле не включается. |
| `items` | Непустой список `{productId, variantId, quantity}`; без повторения variantId; количество целое 1–99. ID варианта должен принадлежать указанному товару. |
| `comment` | Необязательные пожелания до 500 символов, пустое поле не включается. |

В запросе нет email, пароля, платёжных данных, клиентских цен, названий, фото или «подтверждённого наличия». Они не нужны для этой формы. Отдельный тестовый остаток сохранён; старые количества корзины не урезаются.

## Обязанности будущего сервера 10Б

Клиентская проверка не является защитой API. Сервер должен принимать неизвестный JSON, проверять типы и ограничения каждого поля заново, ограничивать размер тела/списка, отклонять неизвестные способы и дубли вариантов. Значения цен, доступности и описаний разрешать по стабильным ID из серверного каталога, а не доверять localStorage. Проверку актуальных цен/остатков окончательно закрыть после 9Г, как требует действующий план.

До ответа об успехе сохранить заказ и снимок точных вариантов в постоянном хранилище. Проверить актуальность кода и адреса ПВЗ через API. Предусмотреть идемпотентность повторной отправки; ключ повтора не должен позволять читать чужие заявки. Недоступное хранилище — ошибка, не успешный заказ в памяти. Принятые данные не помещать в публичные логи; не раскрывать заказ по одному телефону или предсказуемому ID. Форма остаётся закрытой для реальных покупателей до готовности зависимостей плана, включая отправку менеджеру. Хостинг выбирается позже; первый канал менеджеру — Telegram в 10В, см. MANAGER-NOTIFICATIONS.md. Покупателю менеджер пишет в WhatsApp.

| Результат | Будущий HTTP | Поведение формы |
|---|---|---|
| `{ok:true, orderId}` | 201 после постоянной записи | Подтверждение получения заявки; только затем предусмотренная очистка отправленных позиций. Не означает оплату или доставку сообщения. В 10А этот переход отсутствует. |
| `{ok:false, code:'validation', message, fields}` | 422 | Показать ошибки у полей, фокус к первой; ввод сохранить. |
| `cart_changed` | 409 | Показать изменившиеся позиции и обновлённые серверные значения, запросить повторную проверку. Ввод сохранить. |
| `unavailable` | 503 | Сообщить недоступность, оставить ввод и корзину. Текущий адаптер возвращает это локально. |
| `network` / ошибка транспорта | Нет достоверного ответа | Не показывать благодарность и не стирать данные. Будущий повтор — с тем же ключом идемпотентности, чтобы не дублировать сохранённую заявку. |

`GuestOrderResult` фиксирует будущий формат, но не симулирует сервер. UI обрабатывает исключение и ошибки, а успешного экрана пока нет. Реальный сетевой сбой, перезапуск постоянного хранилища и уведомление менеджеру проверяются в следующих заданиях.

## Документация реализации

Context7: проверены [controlled inputs и связь label/input в React](https://react.dev/reference/react-dom/components/input). Поля имеют стабильные id, подписи, `aria-invalid`/`aria-describedby`, `autocomplete`, `type=tel` и `inputMode=numeric` для индекса. Вид настоящей мобильной клавиатуры доступная настольная эмуляция не доказывает.
