# 10В — независимая проверка Telegram

> Этот отчёт фиксирует локальную приёмку до живых отправок. Позднее 11 октября выполнены два заказа через настоящую форму и приём их уведомлений Telegram; видимость обоих подтверждена владельцем. Актуальные квитанции и границы — в [STEP-10V-E2E.md](STEP-10V-E2E.md).

11 октября 2026. Локальная подготовка принята независимым проверяющим. Полностью завершено **13/30**: production-хранилище, актуальные цены/остатки, постоянный запуск обработчика и финальная сквозная приёмка остаются отдельными зависимостями. Живой СДЭК отложен владельцем. Основной сайт `http://127.0.0.1:5173/` доступен, настоящие заявки закрыты.

## Результат проверки

Заявка сохраняется вместе с заданием очереди существующим триггером 10Б. Новый обработчик отправляет сохранённый снимок в заранее заданную группу. Текст содержит номер заявки, ФИО и телефон, точные варианты, количества, цены, сумму товаров, доставку и комментарий. Длинные заявки делятся на пронумерованные части без потери позиций. Принятые части и их идентификаторы сохраняются в D1; после перезапуска они не отправляются заново.

Проверены атомарный выбор задания несколькими обработчиками, ограничение частоты между ними, запрет автоматического повтора при неопределённом результате, ограниченные повторы подтверждённых отказов и ручная сверка точной части в точной группе. Неопределённый результат не означает, что сообщение отсутствует: оператор сначала проверяет группу. Ошибка уведомления не удаляет заказ. Блокирующих замечаний к рассмотренной реализации не найдено.

Область проверки: `lib/telegram-outbox.ts`, `scripts/telegram-local.mjs`, `scripts/configure-telegram.ps1`, миграция `0002_telegram_delivery.sql`, оба новых набора тестов, существующий сервис/контракт/рантайм заявки, конфигурация Vite и миграция 10Б. Проверены все вызовы новых экспортов: в клиентских компонентах и HTTP-маршрутах обработчик не вызывается. Предполагаемая нагрузка — одна рабочая группа и несколько конкурирующих обработчиков одной очереди; постоянный обработчик ещё не развёрнут.

Сборка включает проверку отсутствия серверных маркеров Telegram в клиентских JS/HTML/JSON/map с положительным контролем на исходном серверном модуле. Это проверка границы клиентского пакета без чтения реального token. Предупреждение сборки об `arrow-bubble.svg` присутствовало и в 10Б; к новому обработчику не относится. Семантический переразбор документов graphify не запускался.

Автотесты используют настоящий локальный Miniflare D1 и подставной транспорт Telegram. Они проверяют длинную заявку из 100 позиций, приватный/чужой чат, тему группы, отсутствие прав, два одновременных обработчика, `retry_after`, пять повторов и остановку, испорченный/потерянный ответ, истёкшее владение заданием, потерю подтверждения записи в D1 и полный перезапуск Miniflare между частями. Проверка вводимых команд отклоняет живой запуск без точного UUID/группы и создание тестовой заявки живой командой `demo`. Искусственный режим не обращается к секретному файлу и не использует настоящую сеть.

Обработчик использует фиксированный HTTPS endpoint, запрещает перенаправления, передаёт обычный текст без HTML/Markdown и не выводит контакты, token или ответы провайдера в диагностику. Перед отправкой проверяются бот, точный ID/название/тип группы, членство и право писать. Служебное определение адресата принимает событие членства либо точную команду, адресованную проверенному боту; обычные сообщения и личные чаты не выбирают группу. Ограничения сверены с [официальным Telegram Bot API](https://core.telegram.org/bots/api#sendmessage) и [документацией транзакционного D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch).

## Совпадение базы формы и инструмента

Vite в изолированном режиме использует `.wrangler/order-test`, привязку `DB` и UUID `00000000-0000-4000-8000-000000000002`. Инструмент открывает соответствующее хранилище `.wrangler/order-test/v3/d1` с тем же UUID. Проверяющий открыл эту базу, применил миграцию очереди и прочитал только счётчики/схему: обе прежние заявки и задания остались, попыток отправки нет. Снимки покупателей не выводились. Контрольный файл `artifacts/step-10v/database-probe.mjs` открыл базу за 380 мс и корректно закрыл Miniflare.

Разовый диагностический запуск через `node -e` завис. Он остановлен вместе с собственным дочерним workerd после проверки PID; основной сервер не затронут. Тот же код из сохранённого `.mjs` успешно выполнился. Поэтому для реального запуска использовать штатный файловый CLI. Это наблюдение не является доказательством ошибки SQLite или отправителя.

## Настройка и оставшаяся финальная проверка

По отдельно выполненной ведущим проверке подключены бот `@grace_orders_test_bot` и точная группа **«Тест группа»** типа `group`. `connect --live` сохранил ID в отдельную игнорируемую настройку, отдельный `preflight --live` подтвердил бота, группу, членство и право писать. Независимый проверяющий не читал `.dev.vars`/`.dev.vars.telegram`, не вызывал живые Telegram/СДЭК и не отправлял сообщений.

**На момент локальной приёмки финальная заявка через форму и уведомление ещё не выполнены.** Владелец уже разрешил один вымышленный почтовый заказ с полным ФИО по [каноническому плану](ORDER-TO-TELEGRAM-PLAN.md). Теперь ведущий может выполнить его последним действием: форма → эта изолированная D1 → только новый UUID → проверенная группа. Накопившиеся прежние задания не обрабатывать. Подтверждение API, фактическое появление в группе и прочтение менеджером учитывать отдельно.

GUI диалога ввода Windows не проверен визуально; проверена загрузка встроенного модуля в Windows PowerShell 5.1 с пустым унаследованным `PSModulePath`. Текущая настройка уже сохранена владельцем другим разрешённым способом. Новых зависимостей, публичной команды отправки, административного интерфейса, тем Telegram, расписания и публикации не добавлено. Последующее поручение владельца расширило текущую сквозную проверку: сначала небольшой заказ, затем заказ примерно на 100 000 ₽ с распивами и другими товарами; актуальный порядок — в каноническом плане.

Проверка выполнена в четыре прохода: контракты и путь данных; устойчивость и безопасность; независимые тесты/сбойные случаи; проверка артефактов и статусов. После последнего прохода не осталось замечаний, требующих изменения исходников в проверенной локальной области. Итог живой проверки добавляется отдельно после фактических доказательств.
