# Telegram: настройка и восстановление уведомлений

**Состояние на 11 октября 2026:** бот `@grace_orders_test_bot` и точная группа **«Тест группа»** подключены, ID и права проверены. Два вымышленных заказа через форму на 2 090 ₽ и 99 435 ₽ сохранены и приняты Telegram: `message_id` 3 и 4, по 1/1 части и одной попытке. Владелец подтвердил видимость обоих уведомлений. Повтор завершённых заданий вернул `idle`, предыдущие записи сохранены. [Полный отчёт и квитанции](STEP-10V-E2E.md). Token и ID группы не публиковались. Приём настоящих заявок закрыт; полностью завершено **13/30**.

Последнее поручение владельца разрешило два последовательных вымышленных почтовых заказа, второй примерно на 100 000 ₽ с распивами и другими товарами. Оба отправлены в определённую рабочую группу без предварительного сообщения и повторного общего разрешения. Последовательность — в [ORDER-TO-TELEGRAM-PLAN.md](ORDER-TO-TELEGRAM-PLAN.md).

Telegram заменяет прежний WhatsApp для уведомлений менеджеру по [решению владельца](STEP-10A-OWNER-DECISIONS.md). Менеджер связывается с покупателем через WhatsApp. Уведомления о поступлении сюда не относятся.

## Локальная подготовка

Заявка и задание `order_outbox` появляются атомарно в 10Б. Обработчик читает сохранённый снимок заявки; изменение каталога после её сохранения не меняет содержание уведомления. Данные покупателя не используются как команды, HTML или Markdown. Обычный текст содержит номер заявки, имя и телефон, товары с вариантами, артикулами и количеством, цены и общую сумму, выбранную доставку и комментарий. Отдельно указано, что стоимость доставки уточняет менеджер. Тестовый источник остатков обозначается как тестовый.

Длинное сообщение делится на пронумерованные части. В базе сохраняется подтверждение каждой принятой части, поэтому следующая попытка не начинает весь заказ заново. [Метод sendMessage](https://core.telegram.org/bots/api#sendmessage) ограничивает текст 4096 символами и при успехе возвращает объект сообщения. Это подтверждение приёма API, а не прочтения менеджером.

Принимается только заранее заданная группа или супергруппа. До отправки обработчик проверяет её через `getChat`; личные чаты, каналы и подмена адресата отклоняются. Запросы идут только на фиксированный HTTPS-адрес Telegram, переходы по перенаправлениям запрещены. Token и идентификатор группы передаются только серверу. Клиентского ключа, публичной команды отправки, админ-панели и расписания в этом этапе нет. Темы групп не настраиваются.

## Подготовка бота и адресата

1. Бот уже создан владельцем через [официальный BotFather](https://t.me/BotFather); создавать ещё одного не нужно. Справка по управлению — [руководство BotFather](https://core.telegram.org/bots/features#botfather). Выданный token нельзя пересылать в чат задачи, помещать в исходники, отчёты, снимки экрана или клиентские переменные.
2. Владелец добавил бота в выбранную существующую группу **«Тест группа»**; API подтвердил членство и право писать. Для этого сценария не требуется читать всю переписку: стандартный [Privacy Mode](https://core.telegram.org/bots/features#privacy-mode) сохраняется. Административные права не выдаются автоматически.
3. Доступы сохранены локально в отдельном игнорируемом файле `.dev.vars.telegram`: `GRACE_TELEGRAM_BOT_TOKEN`, `GRACE_TELEGRAM_CHAT_ID`. Token внесён через разрешённое владельцем чтение буфера обмена без вывода значения, ID — успешным `connect --live`; повторный ввод не нужен. Команда нашла единственную группу по точной адресованной команде настройки и проверила её тип/права. Token, ID и переписка в результат не выводятся. При последующих подключениях отсутствие совпадения, несколько групп, личный чат, тема или недостаточные права останавливают операцию. Уже заданный ID только перепроверяется, автоматически на другую группу не меняется.
4. Проверка без отправки завершена: `getMe` подтвердил бота, [getChat](https://core.telegram.org/bots/api#getchat) — ID, точное название и тип группы, `getChatMember` — членство и право писать. Отдельный `preflight --live` повторно прошёл. Первоначальный таймаут и пустые события больше не являются текущей причиной остановки. Это подтверждает доступ, но ещё не отправку заявки; URL с token для вставки в браузер не используются.
5. Подключение обработчика к той же изолированной базе формы проверено. После двух сценариев в ней 4 заявки/4 задания; прежние записи не изменены и не отправлены. Каждый живой запуск был ограничен ровно новым UUID.
6. Два порученных владельцем сценария через форму выполнены с вымышленными контактами. Сохранение заявки/очереди и приём API подтверждены для обоих; фактическое появление обоих подтвердил владелец. Прочтение конкретным менеджером нельзя выводить из ответа API.

Исходный `.dev.vars` не читается и не изменяется. Искусственный режим и тесты не читают `.dev.vars.telegram`; этот отдельный файл используется только при явно выбранном живом режиме. Рабочие секреты не нужны искусственным тестам. При раскрытии token его необходимо заменить через BotFather перед дальнейшим использованием; само тестирование не повод менять ещё не настроенные доступы.

## Локальные команды

Все команды ниже запускаются из `D:/grace`. Секреты в аргументы не подставляются. `connect --live` и `preflight --live` выполнены; затем отдельно отправлены два разрешённых UUID из формы. Команды ниже остаются справкой, повторять отправку завершённых заявок не требуется.

Текущий token уже сохранён, повторно вводить его не нужно. Следующий помощник оставлен как справка для нового файла; существующую настройку он не перезаписывает:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/configure-telegram.ps1
```

Если терминальный ввод неудобен, тот же помощник можно открыть с отдельным окном:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File D:/grace/scripts/configure-telegram.ps1 -UseDialog
```

`-ExecutionPolicy Bypass` относится только к этому процессу; постоянная политика Windows не меняется. Диалог предназначен для Windows PowerShell. После ошибки автозагрузки добавлен явный импорт встроенного модуля Security: его разрешение в Windows PowerShell 5.1 проверено, **реальный показ окна ещё не проверен**. По реализации token вводится в замаскированное поле **Password**, имя **Telegram bot** остаётся прежним; пароль Windows не нужен. Отмена не сохраняет данные. Помощник ничего не отправляет и откажется перезаписывать существующий файл. Текущая настройка уже готова; помощник для неё не требуется.

Искусственный режим использует отдельную базу `.wrangler/telegram-simulation` и подставной транспорт; Telegram не вызывается:

```powershell
node --experimental-strip-types scripts/telegram-local.mjs demo
node --experimental-strip-types scripts/telegram-local.mjs status
node --experimental-strip-types scripts/telegram-local.mjs process --order "<ID искусственной заявки>"
```

`demo` создаёт только искусственную заявку, `status` показывает служебное состояние без контактов, `process` обрабатывает не более одной части. Для следующей части нужен следующий запуск после назначенного времени. Запуск по расписанию не добавлен. В режиме `--live` команда `demo` запрещена.

Для текущей настройки владелец уже написал **в самой группе «Тест группа»** следующую команду; повторять её не нужно:

```text
/grace_connect@grace_orders_test_bot
```

Это служебная команда определения адресата, не тестовое уведомление о заказе. Бот не ответил на неё. После неё успешно выполнено подключение без сообщения:

```powershell
node --experimental-strip-types scripts/telegram-local.mjs connect --live
```

Команда получает `getUpdates` через GET и использует только `my_chat_member` либо точную команду `/grace_connect@<проверенный username бота>` из группы. Обычные сообщения, другая команда и личный чат не выбирают адресата. Проверяются `getMe`/`getChat`/`getChatMember`; единственный допустимый ID сохраняется только в `.dev.vars.telegram`. При неоднозначности выбор блокируется. Отсутствие подходящего события не означает отсутствия группы. Сообщений и ответов на команду программа не отправляет.

Отдельная повторная проверка уже заданной группы без изменения настроек и без сообщения:

```powershell
node --experimental-strip-types scripts/telegram-local.mjs preflight --live
```

Живой режим использует только изолированную базу тестовой формы `.wrangler/order-test/v3/d1`. Доступы читаются только из `.dev.vars.telegram`; случайные переменные окружения не выбираются. Для финального уведомления нужна уже сохранённая через форму вымышленная заявка из [шага 5](ORDER-TO-TELEGRAM-PLAN.md), а не созданная командой `demo`:

```powershell
node --experimental-strip-types scripts/telegram-local.mjs status --live --order "<номер из формы>"
node --experimental-strip-types scripts/telegram-local.mjs process --live --order "<номер из формы>" --approved-group "<проверенный числовой ID группы>"
```

Параметры в угловых скобках — подписи, а не готовые значения. ID берётся только из проверенной настройки; название «Тест группа» вместо него не подходит. Режим отправки требует совпадения указанной группы с настройкой и проверяет вымышленные контактные данные. Сам по себе успешный `status` не проверяет права Telegram и не отправляет сообщение.

## Состояния очереди

| Состояние | Что означает | Действие |
|---|---|---|
| `pending` | Задание ожидает обработки или разрешённого времени повтора | Проверить время следующей попытки и доступность обработчика |
| `sending` | Один обработчик владеет текущей попыткой | Не запускать параллельную ручную отправку той же части |
| `sent` | Все части имеют сохранённое подтверждение приёма | Для подтверждения наличия сообщения отдельно проверить группу; прочтение не доказано |
| `failed` | Автоматическое продолжение остановлено | Разобрать причину и выполнить только предусмотренное восстановление |
| `failed` + `delivery_unknown` | Telegram мог принять текущую часть, но надёжного подтверждения нет | Сначала сверить группу; автоматического повтора нет |

Проверенный ответ об ограничении частоты `429` откладывает следующую попытку не раньше `retry_after`. Согласно [ResponseParameters](https://core.telegram.org/bots/api#responseparameters), это время ожидания в секундах. Без такого значения используется пауза 30 секунд. Подтверждённый отказ `5xx` повторяется с увеличивающейся паузой. Для одной текущей части допускается не больше пяти автоматических повторов; затем `retry_exhausted`. Обычные отправки разнесены минимум на четыре секунды. Перезапуск CLI не отменяет эти ограничения.

Таймаут, обрыв после отправки, непонятный ответ и оставшееся после сбоя `sending` приводят к неопределённому результату. Истечение срока владения попыткой не даёт другому процессу права автоматически отправить ту же часть. Принятые ранее части остаются в базе; заказ не удаляется. API Telegram не даёт этому обработчику гарантии доставки ровно один раз, поэтому сомнительные случаи требуют человека.

## Ручная сверка после неопределённого результата

1. Найти точное задание и номер текущей части. Проверить сохранённого адресата и убедиться, что открыта та же согласованная группа. Не пересылать целиком заявку и контакты в диагностический чат.
2. В группе найти сообщение по номеру заявки и номеру части; сверить содержание. Уже подтверждённые предыдущие части не отправлять снова.
3. Если текущая часть найдена, подтвердить именно её с проверенным идентификатором сообщения и явным указанием, что группа проверена. Это ручное подтверждение оператора, а не автоматическая проверка чтения Telegram. Обработка сможет продолжиться со следующей неподтверждённой части.
4. Если часть не найдена, отсутствие в поиске само по себе ещё не гарантирует, что её не было. Повтор допускается только как явное решение оператора после проверки группы, с признанием риска дубля. Возвращается к обработке только указанная часть; слепой сброс всей очереди или всей заявки запрещён.
5. Если группу или результат достоверно установить нельзя, оставить задание остановленным и решить вопрос с владельцем. Не менять адресата у уже начатой заявки и не помечать сообщение принятым по догадке.

Обычная ошибка доступа или настроек требует сначала исправить причину и повторно проверить группу. Не включать рабочую очередь ради диагностики и не удалять заказ ради повторной отправки.

Сверка конкретной части, уже найденной в группе:

```powershell
node --experimental-strip-types scripts/telegram-local.mjs reconcile --live --order "<номер заявки>" --part 1 --checked-group "<проверенный ID группы>" --action confirmed --message-id "<ID найденного сообщения>"
```

Явно решённый повтор текущей части после сверки:

```powershell
node --experimental-strip-types scripts/telegram-local.mjs reconcile --live --order "<номер заявки>" --part 1 --checked-group "<проверенный ID группы>" --action retry
```

`--part` считается с единицы; вместо примера `1` нужен фактический номер неподтверждённой части. `confirmed` требует положительный проверенный ID сообщения и применяется к `delivery_unknown`. `retry` также допускается после `provider_rejected` или `retry_exhausted`, когда причина устранена. После `destination_changed` сначала вернуть исходную проверенную группу; переназначать уже начатую заявку нельзя. `reconcile` изменяет состояние в базе, но ничего не отправляет. Затем нужно отдельно выполнить `process` для того же номера и группы. При `invalid_snapshot` нужен разбор данных; команда сверки такой случай не возобновляет.

## Что требуется для рабочего запуска

- Настройка бота, точный ID группы, права и изолированный запуск проверены. Оба вымышленных заказа приняты API и подтверждены владельцем; изолированная сквозная проверка завершена.
- Постоянное хранилище заявок, выбранный хостинг и способ регулярного запуска обработчика с наблюдением за остановленными заданиями. В текущем этапе расписание не добавлено.
- Связанные проверки приёмки: актуальные цены/остатки, незавершённая проверка СДЭК, этап 10Г. Локальная проверка очереди не закрывает эти зависимости.
