# Как работать с Context OS

Приоритет: P0 сохранить требования/состояние/точку продолжения; P1 читать выборочно; P2 повысить качество. Это локальный инструмент и протокол агента, не фоновая служба и не гарантированная память модели. Исходные [ТЗ](spec/GRACE_CODEX_CONTEXT_OS_v4.md) и [стартовый запрос](spec/GRACE_CODEX_START_PROMPT.txt) сохранены без изменений. [Решения адаптации](DECISIONS.md).

Все команды из `D:/grace`, Node >=22.13, новых пакетов нет. Одна задача — один Markdown с каноническим JSON-блоком; он содержит исходную формулировку, scope/prohibited/acceptance, даты, владельца, зависимости/риски, verified completed/remaining, проверки, следующий шаг и checkpoint. Не редактировать JSON вручную: инструмент сохраняет исходные требования и добавляет поправки. Не включать секреты и данные клиентов; чувствительный исходный запрос сначала редактировать с владельцем и явно отмечать исключение вместо обещания verbatim.

## Новая задача

Агент сначала интерпретирует текущий запрос, не запускает старую задачу автоматически. Использует известные пути или [INDEX](INDEX.md), создаёт очищенный временный `input.json` вне репозитория:

```json
{
  "owner": "session identifier or UNKNOWN",
  "original": {
    "request": "Дословная доступная формулировка пользователя",
    "provenance": "VERBATIM or faithful reconstruction explicitly marked",
    "scope": "Что требуется изменить",
    "prohibited": ["Что менять нельзя"],
    "acceptance": [{"id": "A1", "text": "Проверяемый результат"}]
  },
  "relevant": ["lib/catalog.ts", "tests/catalog-variants.test.mjs"],
  "dependencies": [],
  "risks": [],
  "remaining": ["A1"],
  "nextStep": "Один следующий безопасный шаг"
}
```

`node scripts/context-os.mjs new <absolute-input.json>` создаёт collision-checked TASK-YYYYMMDD-NNN по московской дате; исходники не читает и команды задачи не выполняет. `relevant` — конкретные файлы, не glob/каталоги. Они автоматически хешируются в checkpoint, включая отсутствующий пока файл как null; `observe` может расширить покрытие, но не убрать relevant. Архив/чужую задачу не подменять новой.

## Продолжение и контрольная точка

1. `node scripts/context-os.mjs resume TASK-...` — read-only чтение именно указанной задачи, перечисление валидной цепочки, сверка Git/хешей, проверка task/registry pointers. Возвращает `taskHash`, `issues`, `differences`, `safeToResume` и nextStep. `EXPECTED` = хеш совпал; изменённый relevant/Git = `UNKNOWN`; непокрытый dirty path = `OTHER_SESSION_OR_USER`. Это классификация для сверки, не доказательство автора изменения.
2. Прочитать task и последний валидный checkpoint, затем реальные изменённые файлы. После штатного commit HEAD отличается от checkpoint: сверить `git show --stat`, хеши relevant и собственный commit, записать ожидаемый переход. Не повторять внешние записи/миграции/отправки автоматически. При неоднозначной или разрушительной операции остановиться и уточнить.
3. После проверенного milestone подготовить временный `checkpoint-input.json`, например:

```json
{
  "state": "IN_PROGRESS",
  "completed": ["VERIFIED: конкретный шаг и источник"],
  "remaining": ["A1"],
  "nextStep": "Следующее конкретное действие",
  "checks": {
    "A1": {"status": "NOT RUN", "method": "node --test ...", "evidence": "Не запускалось", "at": "ISO timestamp"}
  }
}
```

4. `node scripts/context-os.mjs checkpoint TASK-... <absolute-checkpoint-input.json> <taskHash>`: exclusive новый номер → readback → compare-before-rename task → registry последним → проверка ссылок. Использовать hash из своего чтения, не незаметно брать свежий для обхода конфликта. Shared docs также обновлять только после повторного сравнения наблюдённой версии; экспорт `readVersion/writeIfUnchanged` доступен для этого.

Если сбой оставил checkpoint новее task/registry, `resume` показывает расхождение и снимок прогресса. После ручной сверки использовать непустое `reconciliation` с описанием различий; новый checkpoint берёт pending snapshot, сохраняет его completed/checks/amendments. Неверный/повреждённый checkpoint не удаляется и блокирует запись до расследования. Неподтверждённые ручные правки task требуют ручного объединения, автоматически не затираются. Предыдущие checkpoints не редактировать.

## Поправки, пауза и завершение

В checkpoint-input добавить `amendment: {at, basis: "USER_SPECIFIED", text}`; оригинал не меняется. Новые критерии добавляются в `amendment.acceptance: [{id, text}]` с новыми ID. Не прятать новые обязательства только в свободном тексте. `PROPOSED` не меняет критерии без поручения. Любая новая ревизия делает старые свидетельства недостаточными для DONE: их нужно перепроверить/подтвердить для этой ревизии.

Состояния: NEW → IN_PROGRESS → VERIFYING → DONE; рабочая/проверяемая задача может PAUSED/BLOCKED/CANCELLED; из PAUSED/BLOCKED вернуться IN_PROGRESS. DONE/CANCELLED открываются только с явным `reopen` и записью причины. При переключении оставить checkpoint с nextStep и создать независимую задачу. Перед нормальным выходом/рисковым шагом также checkpoint.

DONE требует для **всех** исходных и добавленных критериев `PASS`, непустые method/evidence/at в текущей ревизии, пустые remaining/blockers. `FAIL`, `NOT RUN`, `DESIGN REVIEW ONLY` не подходят. Только явная реальная уступка пользователя допускает `waivers: {"A1": {by: "USER", quote: "точная формулировка", at: "ISO timestamp"}}`. Инструмент проверяет структуру, но не устанавливает истинность PASS/цитаты и не выполняет тест сам: агент обязан реально проверить результат.

`node --test --test-reporter=tap tests/context-os.test.mjs` — изолированные синтетические проверки, temporary Git repos удаляются. `node scripts/context-os.mjs audit` — структура task/checkpoint/registry и локальные Markdown-ссылки; это не свидетельство свежести исходников, для неё использовать resume. `node scripts/context-os.mjs unchanged <baseline.json>` — проверка хешей исходного снимка и новых protected файлов. Установка сохраняет baseline вне Git без содержимого файлов; полная инвентаризация нужна для этой приёмки, не для каждого чата.

Конфликт хеша — остановка перед overwrite; сделанный checkpoint/task остаётся для восстановления. Compare-before-rename не является блокировкой, несколько файлов не атомарны, fsync/защита от аппаратного сбоя не гарантируются. Прямое ручное редактирование/удаление способно обойти проверки. GitHub восстанавливает только отправленные версии, не несохранённый прогресс. Автоматические hooks/синхронизация/численная экономия токенов не добавлялись.

Обновлять только затронутый домен/PROJECT_STATE, с датой и источником; устаревшее помечать, не выдавать за сегодняшнюю проверку. Реестр не дублирует состояние. Завершённые задачи остаются по исходным путям с DONE; архивные исходники не загружать при обычной работе.
